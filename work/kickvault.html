KickVault Vendor Consignment Portal

B2B sneaker consignment portal — KYC, listings, MRNs, invoices, and real-time ops chat.

A public full-stack demo for a fictional company. Not a production product: payments, KYC, and usage in the app are simulated.

01 — OverviewStreetwear consignment, without the paperwork pile

KickVault is a recruiter take-home for a fictional sneaker and streetwear company. The product line is “Streetwear consignment OS — Move product. Not paperwork.” Vendors register, complete a mock PAN KYC check, list sneakers, e-sign material receiving notes, and track commission invoices. Admins review listings, set prices, create MRNs and invoices, approve price and return requests, sync stock, and chat with vendors.

02 — The problemConsignment ops in separate steps

Consignment work is fragmented. Vendors submit stock, operations prices and receives the goods with MRNs, then invoices settlements with commission. Without one shared record, there is no single audit trail for what was listed, received, sold, or returned.

03 — What I builtOne role-based portal

The demo covers the path from KYC to a listing lifecycle, MRN e-sign, commission invoices and PDFs, returns and price requests, authenticated chat, and stock sync.

Vendors can register and log in, pass a mock PAN check in the AAAAA9999A pattern, and are blocked from creating listings until KYC is active. They can create and edit inventory, upload CSV or JSON in bulk, e-sign an MRN and download its PDF, open invoices and PDFs, request a price change or a return, see a payment summary, chat in real time, receive in-app notifications, and upload documents on a 5MB allow-list.

Admins can list vendors, review listings and set prices, create MRNs, create, send, or cancel invoices, approve or reject price and return requests, sync stock from CSV and a protected cron header (x-cron-secret), see sold value on a line chart, and use the same chat and notifications.

A listing moves submitted → priced → live → sold or returned. The API enforces which transitions are allowed.

04 — ArchitectureReact, Django, Postgres, and Redis

The React single-page app, built with Vite, talks REST and JWT to Django REST framework. WebSockets go to Django Channels. PostgreSQL holds the data. Redis backs Channels and Celery.

Login is email-based on a custom user with admin or vendor roles. A vendor profile is either pending KYC or active, and stores PAN and business name. Domain ids are string prefixes: SHOE-1001, MRN-2001, INV-3001, PR-4001, and RR-5001. Money is stored as Decimal. In the seeded data, 1 × ₹17,500 at 12% commission is ₹2,100 commission and ₹15,400 vendor settlement.

Vendors only see their own shoes, MRNs, invoices, chat, and notifications. That limit is enforced in querysets and object permissions, not only by frontend route guards. PDFs are WeasyPrint HTML templates, with a ReportLab fallback when system libraries are missing, which the slim Docker and Render setup needs. GitHub Actions runs the Django tests, the frontend production build, and the Docker image builds.

Open the live app on Netlify. The Render host is the API only and has no interface: https://vendor-consignment-portal.onrender.com

05 — HighlightsWhat holds the demo together

  • Queryset scoping so each vendor only sees their own records
  • Decimal invoice math, including the seeded ₹17,500 commission example
  • PAN KYC gate before a vendor can create a listing
  • WebSocket chat with JWT auth and a room per vendor
  • PDF generation with a ReportLab fallback
  • Docker and GitHub Actions for tests, the frontend build, and images
  • Role-scoped login, JWT with PBKDF2, and a login throttle of 5 requests a minute per IP (429)
  • Cron protected by x-cron-secret, with CORS, DEBUG, and secrets set from the environment
